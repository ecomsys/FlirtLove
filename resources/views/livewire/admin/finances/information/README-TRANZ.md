 # ТЕХНИЧЕСКАЯ ДОКУМЕНТАЦИЯ: Финансы, Транзакции и Возвраты (Refunds)

Документация описывает полный цикл работы финансового модуля админ-панели, включая обработку возвратов (Refund) с использованием очередей (Jobs), событий (Events) и умного отката купленных бонусов.

## 1. Архитектура и Файлы
Финансовый модуль построен по принципам SOLID и Enterprise-архитектуры. Логика разделена на слои: UI, База данных, Сервисы (Эквайринг), Очереди и События.

UI / Контроллер: resources/views/livewire/admin/finances/transactions.blade.php (Volt-компонент).

Модели:
```bash
app/Models/Transaction.php — финансовый лог (содержит методы markAsSuccess, markAsRefunded, аксессоры для UI).
app/Models/SubscriptionPlan.php — справочник тарифов (цены, сроки, фичи в JSON).
app/Models/UserSubscription.php — история покупок подписок юзерами (связь транзакции и тарифа).

Сервис (Эквайринг): app/Services/Payments/MockAcquiringService.php — имитация API банка (для разработки и тестов).
Джоба (Очередь): app/Jobs/ProcessRefundJob.php — фоновый процесс общения с банком.
Событие: app/Events/TransactionRefunded.php — сигнал системе об успешном возврате.
Слушатель: app/Listeners/RevokePurchasedItems.php — автоматический откат VIP/кредитов (запускается через Auto-Discovery).
```

## 2. Принцип работы (Последовательность)

А. Просмотр и фильтрация (UI)

```bash
Модератор открывает страницу транзакций. Volt-компонент через #[Computed] свойства делает три запроса к БД:
counts() — считает метрики для кнопок-фильтров (Успешные, Ошибки и т.д.).
transactions() — жадно загружает (withTrashed) список транзакций с пользователями и их аватарами.
totalRevenue() — суммирует выручку за выбранный период (день/неделя/месяц).
При вводе в поиск срабатывает дебаунс 300ms. Поиск ищет по ID транзакции, Email юзера или ID от банка (provider_transaction_id).
```

Б. Процесс Возврата (Refund) — Пошагово

Возврат средств — это асинхронный процесс. Модератор не ждет ответа от банка, UI не виснет.

```bash
Действие UI: Модератор жмет кнопку "Возврат". Открывается модалка. Модератор выбирает причину из RefundReason Enum и пишет комментарий.
Валидация и Логгирование (Livewire): Вызывается processRefund().
В JSON-поле meta транзакции сразу записывается: кто инициировал возврат, причина и комментарий.
В AdminLog пишется запись: "Инициирован возврат".
В очередь (queue:work) отправляется ProcessRefundJob::dispatch($transaction->id).
Модалка мгновенно закрывается, модератор видит зеленый тост "Заявка отправлена".
Общение с банком (Job + Service): Воркер подхватывает джобу.
Вызывается MockAcquiringService->refund().
Происходит задержка 1.5 сек (имитация сети).
С вероятностью 10% банк "отказывает" (в meta пишется ошибка, статус не меняется, джоба завершается).
С вероятностью 90% банк "одобряет" возврат.
Смена статуса (Защита от Race Condition):
Джоба использует lockForUpdate() внутри транзакции DB::transaction(). Это защищает от двойного списания, если модератор случайно кликнул дважды.
Вызывается метод модели $transaction->markAsRefunded(). Статус меняется с success на refunded. В meta дописывается ответ от банка (MOCK_REFUND_ID).
Откат бонусов (Event -> Listener):
Джоба запускает событие TransactionRefunded::dispatch($transaction).
Laravel (через Auto-Discovery) ловит событие и запускает RevokePurchasedItems.
Финальный UI: При следующем рендере транзакция имеет статус "Возврат", сумма перекрашивается в красный цвет со знаком минус (-500.00 ₽). В модалке деталей доступен JSON-лог переписки с банком.
```

## 3. Бизнес-логика откатов (Слушатель RevokePurchasedItems)

Это самая критичная часть финтеха. Если просто снести is_premium при возврате, мы "украдем" у юзера дни старой подписки, если он продлевал VIP несколько раз подряд.

Слушатель работает умно:

Если откатываем подписку (type = subscription):
Ищет конкретную запись в user_subscriptions, привязанную к этой транзакции.
Аннулирует её (status = canceled, ends_at = now()).
Проверяет, есть ли у юзера другие активные подписки.
Если другие активные подписки есть -> оставляет is_premium = true и корректирует premium_expires_at на срок последней активной подписки.
Если других подписок нет -> полностью сносит is_premium = false и premium_expires_at = null.
Если откатываем кредиты (type = credits):
Декрементирует баланс кредитов в user_preferences.
Использует условие where('credits', '>=', amount), чтобы не дать балансу уйти в минус, если юзер уже потратил подаренные кредиты.

## 4. Связи и Целостность Базы Данных

Финансовые таблицы защищены от случайных удалений, чтобы историческая бухгалтерия никогда не ломалась:

```bash
transactions.user_id -> users.id (nullOnDelete). Если юзер удален, транзакция остается, выводится как "Юзер удален".
user_subscriptions.user_id -> users.id (nullOnDelete).
user_subscriptions.plan_id -> subscription_plans.id (nullOnDelete). Если админ удалил тариф, история покупки сохраняется.
user_subscriptions.transaction_id -> transactions.id (nullOnDelete).
Никаких SoftDeletes в финансовом модуле. Удаление записей запрещено на уровне архитектуры. Отмена операции оформляется сменой статуса (failed, refunded, canceled).
```

## 5. Интеграция с реальными платежками (Stripe, ЮKassa, Apple/Google)

Архитектура на 100% готова к приему реальных денег. Для перехода в продакшен:

Заменить логику внутри MockAcquiringService на реальные HTTP-запросы (Guzzle) к API Stripe или ЮKassa.
При получении реального вебхука об успешной оплате от банка:
Создавать Transaction со статусом success.
Создавать UserSubscription со сроком из SubscriptionPlan.
Начислять юзеру is_premium = true и premium_expires_at = ends_at из подписки.
Весь цикл возвратов (Jobs, Events, Listeners, UI) останется без изменений.
